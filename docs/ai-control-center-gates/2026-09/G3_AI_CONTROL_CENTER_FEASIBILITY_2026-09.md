## 1. 目的と工程境界

G3の目的は、候補手法を選定し、**現在の条件で実行可能か**を確認することである。
代替手法と撤退条件を、重要度・不確実性・費用に応じて決める。

G3では候補比較に必要な最小機能構成を定めるが、詳細な状態遷移、全データ構造、
すべての失敗・復旧経路の固定はG4で行う。実装作業の分割と着手順はG5で行う。

## 2. 最小機能構成（候補比較用）

最小構成は、製品名・プログラム名・個人名ではなく、代替可能な**役割**で表す。候補表では、
これらの役割をどの既存資産又は候補手法で実現するかを比較する。よって、実装候補を入れ替えても
要求する責務、境界、復帰条件は変わらない。

| 役割 | 責務 | 主な入力・出力 |
| --- | --- | --- |
| 利用者入口 | Day選択・Goを受け付け、現在の状態を表示する | 選択Day、Go／状態・停止理由 |
| 人間の責任者 | 目的、権限、費用、受入及び解決不能事象を判断する | 判断記録／継続・縮小・停止・基線保全の指示 |
| 実行管理者 | 選択済みDay、契約、状態、再開先を保持し、許可された遷移だけを実行する | Go・レビュー確認・判断記録／同一Dayの制御状態 |
| 機械的検査者 | 範囲、Git基線、予算、試行、証拠、契約を決定的に検査する | 検査結果／許可・停止理由 |
| 実装・修正担当 | 許可内の計画、実施、限定修正を行い、結果を提出する | 許可済み作業／結果・修正案 |
| レビュー・検証担当 | 報告、証拠、判断の適用範囲と再開条件を独立に確認する | レビュー結果／確認済みの再開条件 |
| 証拠・状態管理者 | 実施、判断、対応ID、停止理由、再開先を追跡可能に保存する | 記録・対応ID／監査可能な状態 |
| 監視・配送担当 | 非同期の報告・応答を相関し、期限・未応答を監視して継続を起動する | 報告・応答／対応済み継続又は停止 |

```text
利用者入口 ──► 実行管理者 ──► 機械的検査者 ──► 実装・修正担当
                    │                 │                  │
                    │                 └────► 証拠・状態管理者 ◄────┘
                    │                                      │
                    └──► 監視・配送担当 ──► レビュー・検証担当 ─┘

許可内の修正: 実装・修正担当 → 機械的検査者 → 同一Dayの再検証

解決不能:
実行管理者 → 人間の責任者（判断要求・証拠・選択肢・再開先）
  → レビュー・検証担当（判断の範囲・証拠・再開先を確認）
  → 実行管理者 → **同一の選択済みDayのPREFLIGHT** → 機械的再検査 → 続行可能な次の処理
```

人間判断は、停止した状態をそのまま解除するだけではない。判断記録をレビュー・検証担当が
確認してから、実行管理者が**Day選択の後**、すなわち同一Dayの`PREFLIGHT`へ戻す。そこで
権限、契約、Git基線、予算、試行及び証拠を再検査する。新しいDayを自動選択せず、選択済みDay
の実施結果を完了扱いにもしない。まだDayを選択していない現在のDay6には、この復帰経路を
適用せず、先に人間の明示選択とGoを要する。
