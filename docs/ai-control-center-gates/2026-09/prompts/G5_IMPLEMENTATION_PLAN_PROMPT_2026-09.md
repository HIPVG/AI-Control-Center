# G5成果物作成プロンプト

> 状態: `SUPERSEDED_BY_G5_V2_PROMPT`。G4 v2は人間承認済みであり、後続の計画化には `G5_IMPLEMENTATION_PLAN_PROMPT_v2_2026-09.md` を用いる。本書は承認前のプロンプトとして保全する。

AI-Control-CenterのG5（実装計画）を作成・更新してください。目的は、承認済みG4設計を、過不足のない独立作業単位、作業カード、テスト計画へ落とすことです。これはG6実装、Day選択／Go、モデル実行、外部配送、費用発生の許可ではありません。

必ず最新の `docs/WORKING_RULES.md`、`docs/CURRENT_WORK.md`、指定されたrunbook、G2要求・トレーサビリティ、G3実現性、G4設計・レビュー記録、現行Git状態を読み、入力の版・ハッシュを記録してください。運用標準の規範本文を優先し、非規範の支援テンプレートは必要十分な範囲だけ既存成果物へ統合してください。文書を増やすこと自体を目的にしないでください。

出力は一つのG5文書に次を含めてください。

1. G5で行うこと・行わないことと、今回の人間許可の境界。
2. 実装順序、要求／リスクとの対応、代案を起動する明確な条件。
3. G0 P01〜P08、G1の未接続／再利用条件、G2 A01〜A06/NFR、G3 M01/M04/M05、G4の限定PASS／未実証を、一つ以上のカード又は明示的`INPUT_BLOCKED`へ対応付ける網羅表。
4. 各作業カードの `work ID`、担当、入力版／ハッシュ、目的、対象パス／API／データ、非目的、前提、許可操作と最大回数、禁止操作、費用上限、期待結果／受領証跡、検証、停止／判断要求、後始末、次状態。
5. fixtureと製品E2Eを混同しないテスト計画。統合E2Eは、未実証の実装要素を隠すためのカードにしない。
6. 各カードが独立して実施・検証・停止できるG5出口判定。

カードは一枚一責任境界とし、設計変更・実装・権限修復・データ移行を混在させないでください。プラットフォーム、UI、エージェントを一枚で同時導入しないでください。可観測性だけを主経路より先にしてはいけません。少なくとも「UIの選択・Go」「server preflightと同一run」「typed evidence判定」「許可内修正→再検証」「通常のレビュー継続」「run単位の手動中継回数・介入理由・上限・実測値」「current/historical表示」「Day 1〜14の契約・preflight入場管理」「選択Dayの受入E2E」を、責務ごとに扱ってください。Day 1〜14の入場管理は全Dayの実行や受入を意味してはいけません。通常の既存レビューバス報告を人間の伝言・個別承認に戻してはいけません。新認証、新配送先、費用、範囲外権限だけを人間判断にしてください。既存M01が実actor E2Eで失敗したときだけ代案M04を再評価し、先回りして実装しないでください。Dayが未選択なら、そのカードを `INPUT_BLOCKED` として保持し、対象Dayを推測して実行しないでください。

各判断は要求ID、G3/G4の根拠、または現行規範へ遡れるようにし、未知値はゼロ・成功・完了へ置換せず明示してください。G5の作成中には、コード変更、テスト実行、サービス起動停止、Day実行、モデル実行、外部投稿、Git変更を行わないでください。
