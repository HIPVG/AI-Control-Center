# AI-Control-Center プロジェクトの目的

作成日: 2026-09-25。状態: 履歴に基づく目的整理案。今回の依頼を最優先し、正式な受入は依頼者が行う。

## 1. 何を作るプロジェクトか

**AI-Control-Center は、利用者が作業対象の Day を選んで Go を押すと、AI 間の指示・実行・評価・必要な修正・再開をつなぎ、その Day の成果を証拠付きで確認できる Windows ローカルの作業実行・管理システムを作るプロジェクトである。**

解決したい問題は、人間が ChatGPT と Codex の間でプロンプトや結果を何度もコピペし、端末コマンドを打ち、停止のたびに作業をつなぎ直すこと。利用者の仕事を「伝言・監視・細かな復旧」から「目的、範囲、費用、重要な判断、最終結果の確認」へ移す。これは履歴の明示的な要望をまとめた解釈であり、現行実装が達成済みという意味ではない。[E01–E04]

最初の利用対象は、別プロジェクト LocalLLM-Lab の Day 1〜14 の研究・検証作業である。AI-Control-Center の価値は、その研究が実際に進むことで測る。自走基盤を整備し続けること、文書を増やすこと、G0 成果物案を作ること自体をプロジェクトの目的にしない。[E03, E05, E08]

## 2. 三つの対象を分ける

| 対象 | 役割 | 完了の意味 |
| --- | --- | --- |
| AI-Control-Center 開発 | 今回作る製品。作業をつなぐ制御・画面・実行管理 | 利用者の操作から実成果、レビュー、停止までが必要な証拠付きで成立する |
| LocalLLM-Lab Day 1〜14 | 最初に製品が扱う業務シナリオ | 各 Day の固有の達成条件を満たす。製品開発の工程番号ではない |
| 標準工程 G0〜G9 | 製品を調査・設計・開発・受入するための進め方 | 各工程の出口を満たす。G0 文書の完成は製品の完成ではない |

## 3. 履歴から読み取れる要求

以下の「要求」はユーザー発言に根拠があるもの。「具体化案」はそれを検証可能にするための今回の提案である。

| ID | 要求 | 根拠 | 具体化案 |
| --- | --- | --- | --- |
| P01 | 人間による AI 間の伝言と端末操作を減らす | E01, E02 | 通常経路では、Go 後にプロンプト・結果・レビューを人間が転送しなくても進む |
| P02 | Day を選び、その日の内容を自動実行する | E03 | Day 契約を読み、現状との差分を把握し、必要な作業を計画・実行する。次の Day は別の明示的許可まで始めない |
| P03 | Day の達成事項を具体的なタスク・実施事項に展開する | E06 | Day 番号に固定スクリプトを結び付けるだけでなく、未達条件に対応した作業と証拠を持つ |
| P04 | 問題時に LocalLLM の対策案を Codex が検査・テスト・実装する思想を残す | E07 | LocalLLM は提案主体であり実行権限を持たない。利用可能性、採否、代替経路を G3 で確認する |
| P05 | レビュー結果に基づく軽微な修正まで自動でつなぐ | E09 | 許可範囲内の修正→再検証→同じ Day の再評価を行う。範囲・費用・権限変更は人間に戻す |
| P06 | 状況を見られ、レビューで軌道修正できる | E04, E10, E11 | Day 番号、全体進捗、未達条件、稼働・待機・判断待ちの違い、証拠、次の動きを表示する |
| P07 | 使える資産で早く実用化し、過剰な基盤強化を避ける | E05, E08 | 実際の Day を進める最小の経路から作り、目的達成に不要な一般化は保留する |
| P08 | 費用を意識しつつ、有用な自走能力を優先する | E12 | 費用・トークン・試行数を見える化し上限で止める。小さな節約だけを目的に実用化を遅らせない |

「Human review はいらない」という過去発言は、人間による日常的な中継や不要な判断待ちを減らす意図として読む。現在の責任者による範囲・費用・権限・最終受入を廃止する許可とは扱わない。

## 4. 最初に成立させる利用の流れ

1. 利用者が対象プロジェクト、Day、許可範囲・予算を確認し、Go を押す。
2. システムが Day の要求、既存成果、Git と実行環境を確認する。安全条件を満たさなければ理由を示して開始しない。
3. AI が未達条件から最小限の作業を提案し、機械的な範囲・権限・予算の検査を経て実行する。
4. 成果を条件ごとの証拠で検査する。問題があれば、必要に応じて LocalLLM 案出と Codex の検査・修正を行う。
5. 必要なレビューを送り、対応する回答を取得・適用する。通常の軽微修正は利用者の伝言なしに継続する。
6. 必要な証拠とレビューが揃えば選択した Day の結果を提示し、その境界で停止する。未達なら完了と表示せず、待機理由又は必要な判断を示す。

これは製品の目標動作であり、今回その操作を実行する指示ではない。停止、再起動からの復旧、回答待ちからの再開は、この経路の一部として設計・検証する。

G2 で対象 Day、実行環境、上限値、証拠の保存先を確定する。現時点で以下の成立は未検証。

| ID | 観測可能な条件 | 必要な証拠 | 対応要求 |
| --- | --- | --- | --- |
| A01 | 実画面の Day 選択・Go から、選択 Day の成果と条件別判定までつながる | UI 操作記録、同一実行 ID の計画・操作・成果・証拠対応表 | P01–P03 |
| A02 | 未達条件と実施作業が対応し、タスク終了だけで Day 完了にならない | 計画との対応、欠落・無効証拠を与えた不合格記録 | P03 |
| A03 | 許可内の修正が検査・再実行・再評価へ戻る。LocalLLM の提案を無審査で実行しない | 提案、採否、変更差分、再検証、試行上限での停止記録 | P04, P05 |
| A04 | 必要なレビューの送信・受領・回答適用・継続を人間のコピペなしで完結する | 対応 ID、各段階の記録、誤回答・重複・期限切れを適用しない記録 | P01, P05, P06 |
| A05 | ダッシュボードが Day 番号、全体進捗、未達条件、現在状態、次の動きを表示し、実行・待機・判断待ち・停止を区別できる。停止命令・再起動・予算超過で勝手に作業を増やさない | 表示と同一実行 ID の保存状態・証拠の照合、中断復旧、範囲外拒否、次 Day 非開始の記録 | P02, P06, P08 |
| A06 | 実際の LocalLLM-Lab の成果が一つ以上進み、利用者の中継負担と実行コストを確認できる | 対象成果の受入記録、Go 後の手動中継回数・介入理由・費用・トークン・試行数。通常経路の手動中継は 0 回を目標 | P01, P07, P08 |

模擬テストは部品の安全性確認に使うが、実環境の A01/A04/A06 の代替にはしない。製品の受入と研究結果の学術的・業務的妥当性は別々に判定する。

## 6. 初期範囲と非目的

初期範囲は Windows、ローカル画面、現在の Day 1〜14 シナリオ、既存の制御・証拠・レビュー資産の再利用。現在の技術制約は Python 3.12 / FastAPI / Uvicorn / Pydantic / HTML・CSS・vanilla JavaScript、既定接続先 127.0.0.1、JSON 永続化インターフェースである（現行 AGENTS.md）。

今回の目的ではないもの:

- G0 案の生成を最終成果とすること。
- Day 1〜14 を無断で一括実行すること、任意の新シナリオへの拡張。
- あらゆる業務を扱う万能エージェント基盤や、新しい管理インフラを先に作ること。
- 既存ファイル・状態・実験結果を削除してゼロから実装すること。
- AI の成功宣言やテスト件数だけで、製品・Day の完了を認定すること。
- M365 Copilot 向け業務支援、製造業向け商品企画、モデル比較自体を、この製品の新しい必須機能に取り込むこと。

## 8. 今回の訂正と残る判断

以前の G0 v1/v2 は「G0 案の作成」の受入条件を中心に置き、開発対象を取り違えていた。その目的・受入・工程判断を本書と訂正版 G0 に置き換える。旧文書の自己確認を製品目的の妥当性の証拠にしない。

今回許可された作業は、目的の文書化、保存済み計画・プロンプトの訂正、そのプロンプトによる G0 案の再作成と保存まで。製品開発の全工程を実行する許可ではない。

今後確定する判断は、最初に実証する Day と範囲、実行予算・時間・試行上限、外部接続の利用条件、レビュー担当の委任範囲、製品受入の具体的環境・期限である。**製品の目的そのものを UNKNOWN として差し戻す必要はない。**
