## Implemented behavior

- Added one composition layer that binds the already accepted Evidence, repair,
  review-continuation and human-decision controllers to the durable `RunRecord`.
- Existing Day state is projected to `RunControl` only after Day, contract and run
  identity checks. A reported Day `COMPLETE` cannot be projected unless all retained
  criterion Evidence is validator-owned and bound to the same run.
- Provider results pass through `CompletionEvidenceEvaluator`; wrong run, criterion,
  configuration, type or invalid content is not retained and cannot advance state.
- Bounded repair results are persisted as versioned updates of the same immutable
  intent. Scope/Git/budget failure and attempt exhaustion do not consume or mutate a
  later state. Matching review returns the same run and Day to `PREFLIGHT`.
- Review transport is represented only by injected deterministic events. A response
  needs exact `IN_REPLY_TO`, a valid continuation envelope, a downstream effect and
  matching readback before the same run returns to `PREFLIGHT`. Stale, duplicate and
  absent-effect responses remain non-completing.
- Human words are bound to one decision ID and one run. Only the accepted human
  decision plus a fully matching reviewer confirmation and verified downstream
  effect returns that same run to `PREFLIGHT`.

No real Watcher, service, browser, model or Day was started. The existing accepted
controller contracts and G4 state semantics were not changed.

## Review rejection and bounded repair

Pack `G6-RI01-COMPLETION-20260929-001` was rejected at implementation commit
`61c59621de4d0d4c2b0fddce0838f640332e1e50`. The accepted defect classification
was an RI-01 implementation gap: `project_day_state` checked Day and contract but
did not prove that the snapshot belonged to the target run or that the target was
the current run.

The bounded repair adds an optional, backward-compatible `run_id` to the Day
snapshot. The production composed executor passes the RI-00 run ID into the Day
controller. Projection now rejects before update unless both the store's current
record and the snapshot carry the exact target run ID. A focused assertion creates
two runs with the same Day and contract, then proves that projection to the
historical run and projection from a mismatched snapshot both reject without
changing either record.
