## Exact-run composition

- The current RunRecord is selected by the persisted RunStore; every other persisted
  run is projected only as history.
- Admission is reconstructed from the first stored version of that same run.
- Day criteria are joined only when the snapshot run ID, selected Day and contract
  fingerprint all match the current RunRecord.
- Telemetry is loaded only through the current run ID. Stored run-ID mismatch or
  unreadable telemetry is omitted and recorded as a projection error.
- Optional review, human-decision and runtime observations are accepted only when
  Pydantic's exact-run identity guard matches the current run; otherwise all optional
  inputs are omitted with an explicit error rather than partially applied.
- Unknown telemetry values retain `value: null`, reason and source semantics. No
  unknown value is inferred as zero.

## Failure and restart behavior

- An unreadable run collection or corrupt version history returns no selected/current
  run. It is not projected as current or complete.
- Snapshot or telemetry mismatch leaves the authoritative RunRecord in its persisted
  state but does not project criteria or mismatched telemetry into it.
- Re-created RunStore, telemetry-store and controller instances rebuild the same one
  current run and distinct history, proving the read path does not depend on the old
  process-start singleton.
- An API assertion adds a RunRecord after the FastAPI application already exists and
  confirms that the next GET sees it through the real engine composition root.
